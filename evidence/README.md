# Plan-available steering: replication and figure data

## Results and scope

The twelve synthetic scenario cells combine two tyre-force friction caps (0.90 and 0.45), two steering maneuvers and three phase seeds. Seeds were reused by design across surface and maneuver cells. Fourteen origins occur within each trajectory. The 216 trajectory-level RMSE values are the product of 12 scenarios, two models, three matched fit seeds and three information conditions. The paired summary uses three fit seeds per model. The unit for steering angles is rad and the unit for yaw-rate RMSE is rad/s.

A holds the actual wheel angle at prediction origin. B maps the command plan issued at that origin through the prescribed causal rate-limited wheel actuator. C replays the realized wheel angles under later replanning. Constant speed, origins, initial state, history and truth are shared. For this synthetic driver, the actuator model in B exactly matches the plant actuator. Differences between the wheel sequences for B and C arise when the controller issues revised plans. The prescribed actuator is not a calibration obtained from KIT. No KIT, LMSD or LVMS test trajectory was used to fit these settings or generate the synthetic truth.

## Files

* paired_trajectories.csv is the plotting table. For each of data_A through ode_C, we calculated one yaw-rate endpoint RMSE across the 14 forecast origins within a trajectory for each fit seed. The reported value is the arithmetic mean of the three seed-specific RMSEs. gap means ODE minus data-only. wheel_B_C_rms_rad is the RMS separation between the origin-issued mapped wheel path and realized wheel path. issued_command_C_rms_rad compares the unfiltered original command path and realized wheel path.
* per_fit_trajectory.csv contains all 216 rows before averaging training seeds. summary.json contains the overall and maneuver-specific results. protocol.json is the immutable protocol registered before truth generation. evidence.json contains the hashes of the remote archive including compact files and full arrays. Full raw states, timestamped command packets, per-origin results, and exact run source remain in the project execution archive under publication_ai_20261121_planned_steering/.
* gpu_audit_registration.json and gpu_audit_result.json document the subsequent numerical audit using the already-generated arrays. The original GPU, RTX 5090 with TF32 disabled, reproduced all 36 trajectory-by-mode model rankings. Individual endpoint values differ between CPU and CUDA.
* reproduce/planned.py and reproduce/gpu_audit.py are execution code. To avoid embedding machine-specific paths, the release copy of planned.py resolves the archive base from the KIT_PROJECT_ROOT environment variable instead of the original host path. Output file evidence.json and protocol.json retain the execution-time SHA of the original script. The reproduction copy has its own SHA in the local release manifest. Generate a new protocol with the portable script in an empty working copy before running it.

## Frozen model provenance and reproduction

The two compared models were the same KIT two-state MLP trajectory architecture. The data arm used endpoint supervision alone; the ode arm added the continuous dynamics residual during training. All six final, 1000-epoch checkpoints (data/ode, seeds 11, 22 and 33) are from the frozen KIT training cohort recorded in frozen_cohort.json. These are project-trained weights; the article publishers do not distribute them. Their exact individual SHA-256 digests are listed in protocol.json under original_files. No optimization occurs during inference. The wheel/tire geometry and calibrated effective stiffnesses are read from the frozen kit_contract.json.

Set KIT_PROJECT_ROOT to the local copy of the original research archive root. The loader expects vsd_new_sources_v2_20261114/execution_20261115/{kit_contract.json,kit_models.py,official_build_network.py,integration_result.json,frozen_cohort.json,runs/{data,ode}_seed{11,22,33}/final.pt}, together with its export_validation/vendor dependencies. The freeze step also records the prior simulator hash from publication_vsd_20261118/simulation/baseline_interface_repair/independent.py. The optional audit identifies the archived GPU through publication_vsd_20261118/factor/gpu_reproduction/protocol.json. Checkpoints and the KIT implementation are retained in the project archive. Prospective sharing of restricted data or third-party source must follow their original terms.

Use a fresh copy of the reproduce directory, Python with NumPy and PyTorch as recorded in protocol.json, and one BLAS/OpenMP thread. Run python planned.py freeze and then python planned.py run. Compare the resulting CSV values with the provided plotting tables. The simulator archive saves plans alongside issue indices; multiplying those indices by 0.02 s gives publication times. To check the CUDA backend, set CUBLAS_WORKSPACE_CONFIG=:4096:8 and run python gpu_audit.py on an available matching GPU. The CPU reconstruction check in reproduce/gpu_audit.py requires the largest absolute trajectory RMSE difference from the archived CPU values to be below 1e-12 rad/s. Observed CPU reconstruction errors, CPU-to-GPU differences and ranking agreement are reported in gpu_audit_result.json. The reported scientific estimates use the prospective CPU run.
